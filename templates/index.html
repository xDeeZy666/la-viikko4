1. How server B was created

Firstly I shut off A with sudo poweroff, took a snapshot in cPouta, started A again and launched B from the snapshot (flavor standard.medium, same key and security group), and gave B its own floating IP 195.148.20.47.

4. Hourly backups and continuous replication

Hourly backups: Cron runs the script as root at minute 0 of every hour. The script uses rsync over SSH to copy A's /var/www/html to a new timestamped folder in /var/backups/www-from-a/ on server B and writes OK or FAILED for every run to /var/log/www-backup.log. The newest 48 backups are kept.

Replication: A is the primary, it writes every database change to its binary log. B connects to A as the user "replicator" and continuosly fetches and applies the changes to its own database, usually within seconds.

Why replication does not replace backups: Replication copies every change to B within seconds, including mistakes. If a table is deleted or wrong data is written on A, the same happens on B. Backups are older versions from different points in time, so it's possible to restore data as it was before the mistake

6. What I learned

When B was cloned from A, it also ran the Week 2 app, which tries to increment the counter on every page load. On a read-only replica this would fail, and the replica should never be written to by an application anyway. I solved it by disabling the service on B with "sudo systemctl disable -- now viikko2", so only the viikko4 app runs there.
